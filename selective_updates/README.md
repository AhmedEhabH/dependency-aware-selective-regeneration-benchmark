# Selective-Update Ledger

## Purpose

This folder is the canonical operational change ledger for the project. It records every production change (code, data, notebook, config, bundle) with measured impact metrics. It enables:

1. **Traceability** — link requirements → canonical artifacts → generated derivatives → validation
2. **Impact measurement** — compare selective vs full regeneration (time, tokens, defect detection)
3. **Governance** — enforce selective-update policy; no merged change without a record
4. **Handoff** — new agents read the ledger to understand project state and conventions

## Relation to Selective-Regeneration Research Idea

The selective-regeneration research idea (from the paper) proposes minimizing LLM-assisted code changes by regenerating only affected artifacts. This ledger is the *engineering implementation* of that idea for the benchmark infrastructure itself — not the research subject. We measure our own selective updates to validate the approach works in practice before applying it to the research.

## Canonical Sources vs Generated Derivatives

| Category | Examples | Ownership |
|----------|----------|-----------|
| **Canonical Sources** | `seven_arm_benchmark.py`, `src/benchmark/**`, `benchmark_data/**`, `configs/**`, `notebooks/**`, `pyproject.toml` | Human-edited, Git-tracked, single source of truth |
| **Generated Derivatives** | `project/kaggle_upload/**` (code, data, notebooks) | Machine-generated by `scripts/build_upload_bundle.py`, regenerable, must match canonical SHA-256 |
| **External Immutable** | `<parent>/inputs/**` | Outside Git, never modified |

## When a Change Record Is Required

Create a record under `records/SU-XXXX-*.md` for every merged change that:

- Modifies production code (`src/benchmark/**`, `seven_arm_benchmark.py`)
- Modifies benchmark data (`benchmark_data/**`)
- Modifies execution configs (`configs/**`)
- Modifies notebook (`notebooks/seven_arm_benchmark.ipynb`)
- Modifies deployment bundles (via bundle builder)
- Modifies operational docs (`START_HERE.md`, `PROJECT_HANDOFF.md`, `SELECTIVE_PROJECT_UPDATE_POLICY.md`)

**Exceptions:** Trivial typo-only edits that do not affect operational instructions may skip the record.

## Change ID Assignment

Sequential: `SU-0001`, `SU-0002`, `SU-0003`, ...

Assigned when the change branch is created or when the record is started.

## Metrics Collection

Each completed change appends one JSON object to `metrics/change_metrics.jsonl`. Fields:

- `change_id`, `date`, `requirement_type`
- `canonical_files_affected`, `derivative_files_regenerated`, `unaffected_files_preserved`
- `lines_added`, `lines_deleted`
- `targeted_tests_run`, `full_tests_run`, `test_failures`
- `engineering_elapsed_seconds` (null if not measured)
- `agent_model`, `agent_tokens` (null if not available)
- `defects_detected`, `defects_introduced`
- `quality_result`: `preserved` | `improved` | `degraded` | `unknown`
- `branch_commit`, `merge_commit`, `deployment_status`

**Never invent token counts or elapsed time.** Use `null` when unavailable.

## Records and Git Commits

Each record corresponds to one merge commit on `main` (via `--no-ff`). The record links to:
- `branch_commit`: tip of the change branch before merge
- `merge_commit`: the merge commit on main
- `final_main_commit`: main after merge (same as merge_commit for --no-ff)

## Prohibition on Unmeasured Quality Claims

**No record may claim quality improvement without measured evidence.**

- `quality_result: improved` requires: before/after test pass rate, or benchmark comparison, or defect reduction with data
- `quality_result: preserved` is the default for refactoring/infrastructure
- `quality_result: degraded` if tests fail or defects introduced
- `quality_result: unknown` if no relevant tests exist

Claims like "cleaner code" or "better architecture" without metrics are not evidence.
